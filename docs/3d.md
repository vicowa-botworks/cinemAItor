# 3D Support (MS-8)

CinemaItor treats 3D content as a first-class asset type: import a model, preview it interactively
in the browser, and reuse rendered views of it as `@references` in prompts, panels and shots.

## Scope (v1)

| Capability                                                                                         | Status                                                            |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Upload `.glb`, `.gltf`, `.obj` (GLTF binary/JSON + Wavefront OBJ)                                  | Shipped                                                           |
| Upload `.fbx`, `.usd`, `.usdz`, `.stl` as `model` assets (stored, no inline preview)               | Shipped                                                           |
| Inline 3D preview in Asset Detail (three.js: orbit, zoom, pan; grid + hemisphere/key/fill lights)  | Shipped (glb/gltf/obj)                                            |
| View export: front / side / top / perspective 1024px PNGs stored as image assets `@<model>_<view>` | Shipped                                                           |
| Re-export: re-renders stored as a **new version** of the existing view asset (never overwrites)    | Shipped                                                           |
| FBX/USD preview                                                                                    | Deferred (requires additional loaders + GLTF-USDZ transpile path) |

## Asset type

- `asset_type: "model"` — a normal asset row (global or project scope, unique `@slug`, aliases,
  tags, immutable versions). The backend is deliberately permissive: model files upload, version and
  preview (raw bytes) without proxies or thumbnails; the timeline placement picker and the backend's
  media-kind gate simply don't offer `model` assets for timeline tracks (they are reference
  material, not render sources).
- Registered media types (`storage/media_types.ts`): `model/gltf-binary`, `model/gltf+json`,
  `model/obj`, `application/octet-stream` (FBX), `model/vnd.usd`, `model/vnd.usdz+zip`, `model/stl`.

## Upload metadata

The raw-bytes upload protocol accepts one optional extra header (see `docs/assets.md`):

- `X-Technical-Metadata` (optional, percent-encoded JSON): merged into the version's
  `technical_metadata_json`. Used by the view-export flow to attach `provenance` metadata to each
  derived image version.

## Frontend

- `frontend/src/model-views.js` — pure, unit-tested camera-pose math: `VIEW_SPECS` (`front`, `side`,
  `top`, `perspective`), `viewCameraPose(bbox, view, margin, fovRad)` (unit direction per view,
  distance = `radius * margin / tan(fov/2)`, unknown views fall back to `front`),
  `modelFormatForFile()` (filename → loader format: `gltf`/`obj`, `null` for everything else).
- `frontend/src/components/model-viewer.js` — the `<model-viewer>` web component. three.js and the
  loaders (OrbitControls, GLTFLoader, OBJLoader) are pulled from the import map in
  `frontend/index.html` (esm.sh CDN) and the module itself is **dynamically imported** by Asset
  Detail, so a CDN outage or missing WebGL degrades only the 3D preview. The model is normalized
  (centered at the origin, scaled to a unit bounding sphere), the camera frames it with the shared
  `viewCameraPose` math, and `exportViews()` renders each standard view to a 1024px square PNG blob,
  pausing the interactive animation loop for the capture and restoring it afterwards. It dispatches
  `model-views-exported` (`detail: { views: [{ view, blob }] }`).
- `frontend/src/components/asset-detail.js` — the model branch of the preview pane renders
  `<model-viewer>` for glb/gltf/obj versions (other model formats show a "preview not available"
  placeholder). Below the preview, model assets get an **Export derived views** section:
  - "Export 4 views" calls `viewer.exportViews()`, then for each view stores a fresh image asset
    `@<model>_<view>` (same scope/project as the model) and uploads the PNG as its first version
    with provenance metadata
    (`provenance: { kind: "derived_view", view, source_asset_id,
    source_asset_name, source_version_number }`).
  - Re-exports reuse the existing view asset: on a 409 slug conflict the flow finds the asset by
    slug and stores the new render as a **new version**, so every re-export is audit-able and
    restorable like any other version.
- Derived views are plain `image` assets, so they flow everywhere images do: `@<model>_<view>`
  references in prompts, panels, shots, and the review board.

## Exported view slugs

| View        | Slug                   | Camera                            |
| ----------- | ---------------------- | --------------------------------- |
| front       | `@<model>_front`       | +Z, looking at the centered model |
| side        | `@<model>_side`        | +X                                |
| top         | `@<model>_top`         | +Y (down the unit up-axis)        |
| perspective | `@<model>_perspective` | normalized (1, 0.65, 1) diagonal  |

All views use a 30° vertical FOV with 1.3× margin around the fitted bounding box.

## Deferred

- FBX and USD/USDZ inline preview (loaders + USDZ→GLTF transpilation), stl preview.
- View exports for non-GLTF formats (there is nothing to render without a loader).
- Multiple exported sizes, EXIF-style orientation handling for odd camera rigs, and baking the
  exported views into a contact-sheet image.
